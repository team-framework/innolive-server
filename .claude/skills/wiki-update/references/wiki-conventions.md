# 위키 규약 요약

`SKILL.md`가 참조하는 계약이다. **정본은 위키 안의 `_메타데이터_가이드.md`** 이고, 이 문서는 작업 중 빠르게 확인하기 위한 요약이다. 충돌하면 정본을 따른다.

## frontmatter

모든 문서는 **첫 줄부터** 아래 순서로 시작한다.

```yaml
---
domain: [server]
question: "이 문서가 답하는 질문 하나"
owner: server-team
verification: code-verified
type: reference
status: current
scope: server
as_of: 2026-08-15
last_verified: 2026-08-15
visibility: team
---
```

### 정본이 규정하는 4필드

앞의 넷은 정본이 값과 의미를 못박은 **계약**이다. 순서도 이대로여야 한다.

| 필드 | 의미 | 값 |
|---|---|---|
| `domain` | 어느 영역인가. 한 개여도 배열 | `product` / `server` / `ai` / `client` / `shared` |
| `question` | **검색 라우팅 키.** 이 문서가 답하는 질문 하나 | 아래 작성 규칙 |
| `owner` | 작성자가 아니라 **정본 책임 팀** | `server-team` / `client-team` / `ai-team` / `framework-team` / `wiki-maintainers` |
| `verification` | 본문을 뒷받침하는 근거 수준 | 아래 등급표 |

- `domain`에 `shared`를 다른 값과 섞지 않는다. `shared`는 "여러 도메인"의 축약이 **아니라** 공통 프로세스 자체를 다룰 때만 쓴다. 관련 영역을 나열할 수 있으면 `[server, ai, client]`처럼 적는다.
- `domain`은 **폴더 위치와 달라도 된다.** 서버 지식베이스 안에 있어도 AI 레포를 설명하는 문서면 `[ai]`다.
- `owner`는 한 문서에 **하나만.** 두 팀의 계약 문서라면 실제 변경을 승인·반영하는 쪽을 적고, 나머지 영역은 `domain` 배열로 표현한다. 담당이 바뀌면 문서를 복제하지 말고 `owner`를 고친다.

### 나머지 필드 — 정본이 규정하지 않는다

정본은 이 넷에 대해 *"기존 속성이 있다면 네 필드 뒤에 그대로 유지한다"* 고만 말한다. **값 목록도 필수 여부도 정해진 바 없다.**

아래는 규약이 아니라 **현행 147문서의 실측 분포**다. 새 문서는 여기 맞추되, 목록에 없는 값이 필요하면 **지어내지 말고 담당 팀에 확인**한다.

| 필드 | 실측 값 (빈도순) |
|---|---|
| `type` | `reference` 133 · `hub` 7 · `incident` 5 · `guide` 2 · `runbook` 1 · `how-to` 1 |
| `status` | `current` 146 · `historical` 2 · `draft` 1 |
| `scope` | `server` 55 · `ai` 36 · `client` 34 · `product` 16 · `common` 5 · `wiki` 1 |
| `visibility` | `team` — **사실상 단일값** |

`as_of`·`last_verified`는 `YYYY-MM-DD`. **둘의 차이는 정본에도 정의돼 있지 않고**, 현재는 함께 갱신하는 관행이다.

`domain`(배열)과 `scope`(단일 문자열)의 대응도 정의돼 있지 않다 — `domain: [shared]`인 문서가 `scope: common`과 `scope: wiki`로 갈린다. 배열 원소의 **순서 규칙도 없다**(`[server, ai]`와 `[ai, server]`가 함께 쓰인다). 새로 정하지 말고 **가까운 기존 문서를 따른다.**

## question 작성 규칙

`question`은 제목의 반복이 아니라 **LLM이 이 문서를 골라야 하는 사용자 질문**이다.

```yaml
# 좋음
question: "AI 워커를 재시작하기 전에 무엇을 확인하고 이후 어떻게 검증해야 하는가?"

# 나쁨 — 질문이 아니라 라벨
question: "AI 워커 문서"

# 나쁨 — 무관한 질문을 합침
question: "AI 워커는 무엇이고 배포는 어떻게 하며 장애는 왜 났는가?"
```

1. 완결된 한국어 의문문 **한 문장**. `?`로 끝낸다
2. 항상 **큰따옴표**로 감싼다 (YAML 해석 오류 방지)
3. 무관한 질문이 둘 이상이면 억지로 합치지 말고 **문서를 나눈다**
4. 문서의 핵심 범위가 바뀌면 제목뿐 아니라 `question`도 **함께** 고친다

## verification 등급

근거 수준에 맞는 것을 고른다. 확신이 없으면 낮은 쪽으로.

| 값 | 언제 |
|---|---|
| `runtime-verified` | 실제 실행·로그·실기기·운영 관측으로 확인 |
| `code-verified` | 현행 코드·스키마·테스트를 직접 대조 |
| `source-verified` | 외부 1차 자료나 명시된 정본 원문과 대조 |
| `team-confirmed` | 팀이 정한 규칙·결정·역할을 확인 |
| `mixed-verified` | 코드·런타임·git 이력·팀 결정 등 둘 이상이 섞임 |
| `partial` | **핵심 내용 일부가 미검증·불완전·노후** |
| `chat-derived` | 채팅·메모에서 추출했고 아직 대조 전 |
| `unverified` | 출처나 검증 근거가 아직 없음 |

`partial`과 `mixed-verified`는 다르다. 증거가 여러 종류라는 이유로 `partial`이 되지 않으며, 반대로 **중요한 미검증 항목이 있으면 검증된 단락이 많아도 `partial`** 이다.

`partial`·`chat-derived`·`unverified` 문서는 **정본처럼 인용하지 않는다.**

### 등급을 조정할 때

**올릴 때** — 근거가 실제로 생겼을 때만.

| 새로 생긴 근거 | 등급 |
|---|---|
| 코드·스키마·테스트를 직접 대조 | `code-verified` |
| 실행·로그·실기기·운영 관측 | `runtime-verified` |
| 외부 1차 자료·명시된 정본과 대조 | `source-verified` |
| 팀이 정한 규칙·결정·역할을 확인 | `team-confirmed` |
| 위의 둘 이상이 섞임 | `mixed-verified` |

**내릴 때** — 이쪽을 빠뜨리기 쉽다.

- 검증된 문서에 **미검증 내용을 추가**했으면 `partial`로 내린다. 정본: *"본문에 중요한 미검증 항목이 있으면 검증된 단락이 많아도 `partial`이다."*
- 본문 일부가 낡았음이 확인되면 `partial`로 내리고 **무엇이 낡았는지 본문에 적는다.**
- 등급을 그대로 두고 내용만 보태면 **검증 수준을 과장하게 된다.** `partial`·`chat-derived`·`unverified`를 정본처럼 인용하지 않는다는 규율이 그만큼 무력해진다.

## 층 구조

```
innolive.md                 1층 라우터
├ 서버.md / 클라이언트.md / AI.md      2층 도메인 허브
├ _현행_수치.md               변동 수치 단일 출처
├ _메타데이터_가이드.md         계약 정본
├ _외부_정본_목록.md
├ GPU 서버 인수인계 및 운영 가이드.md
├ 지식베이스/
│   ├ _00_서버_… / _01_클라이언트_… / _02_AI_…   3층 색인
│   └ 7갈래 폴더 = 4층 실문서
└ 기획/ · 팀·일정/
```

**7갈래**: 규약 · 레포·자산 · 아키텍처 · 운영 · 연동 · 성능·평가 · 사건기록

## 도메인 접두

세 도메인이 같은 갈래 폴더를 공유한다.

| 접두 | 도메인 |
|---|---|
| 없음 (`01_`, `02_`…) | 서버 |
| `C` (`C01_`…) | 클라이언트 |
| `A` (`A01_`…) | AI |

## 표기 규율

**`[당시]`** — 과거 상태를 서술할 때 반드시 붙인다. 붙지 않은 과거 서술은 결함이다.

**변동 수치 단일 출처** — 배포 태그·`MAX_SESSIONS`·용량 등 바뀌는 값은 `_현행_수치.md`에만 적고, 다른 문서는 링크만 건다. Obsidian 임베드(`![[...]]`)는 쓰지 않는다 — RAG 색인기가 펼치지 못한다.

**이슈·PR 번호** — 레포를 명시한다. `server#100` / `client#74` / `ai#1`. 세 레포의 번호가 서로 겹친다.

**사람 이름** — `팀·일정/`은 실명, `지식베이스/`는 GitHub ID를 쓴다. 대응표는 `팀·일정/팀 구성.md`가 정본이다. 팀원을 가리킬 때 "사용자"라고 쓰지 않는다 — **"사용자"는 제품 사용자 전용**이고, 팀원은 역할("서버 담당"·"AI 담당"·"클라이언트 담당")로 적는다.

**사적 정보** — 개인 이메일·자격증명 값·개인 홈경로·SHA-1 지문은 **존재만 표기**하고 값을 옮기지 않는다. 커밋 SHA와 호스트명은 허용.

## 문서를 새로 만들 때

기존 문서의 `question`과 겹치면 **만들지 않고 병합**한다. 신규는 "기존 어느 문서의 질문에도 붙지 않는다"가 설명될 때만.

만들었다면 해당 3층 색인과 2층 허브에 링크를 추가하고, **문서 수 카운트**도 함께 갱신한다.
